# Developing Campfiremons

How the pack is built, tested, released and hosted. Players only need [README.md](README.md); the design brief
(stages, gating, mod list, update path) is [DESIGN.md](DESIGN.md).

This repo is a [packwiz](https://packwiz.infra.link/) pack. Mods are stored as small `.pw.toml`
metadata files (download URL + hash), never as jars.

## Layout

| Path | What |
|---|---|
| `pack.toml`, `index.toml` | packwiz pack metadata (`index.toml` is generated by `packwiz refresh`) |
| `mods/`, `resourcepacks/`, `shaderpacks/` | one `.pw.toml` per file |
| `config/` | configs we ship; `config/defaultoptions/` holds the official pack's first-launch defaults |
| `kubejs/` | our scripts (`startup_scripts/`, `server_scripts/`, `client_scripts/`) and datapack files |
| `tools/` | dev scripts (not shipped to players, see `.packwizignore`) |
| `tools/release/` | `build.py` (the release zips) and the server starter: the launcher (`server/launcher/Launcher.java`) and `start.sh` |
| `.github/workflows/` | `release.yml` publishes a GitHub Release per `vX.Y.Z` tag; `check.yml` fails on a stale `index.toml` |
| `README.md` | the player-facing page: install, joining, how the pack plays |
| `CHANGELOG.md` | one section per version, used as the release notes |

## Dev setup (once)

```sh
go install github.com/packwiz/packwiz@latest   # installs ~/go/bin/packwiz
sh tools/setup-dev-instance.sh                 # creates the "Campfiremons Dev" Prism instance
```

Restart Prism if the instance doesn't show up.

## Dev loop

- Press Play on **Campfiremons Dev**. Its pre-launch hook (`tools/dev-prelaunch.sh`) runs
  `packwiz refresh` and then syncs mods/configs from this repo into the instance.
- `kubejs/` and `config/ftbquests/` in the instance are symlinks to this repo. Script edits are
  live: `/reload` re-runs server scripts, and `/kubejs reload startup` re-runs startup scripts
  (where the Cobblemon gating lives). The in-game quest editor saves straight into git.
- Logs (KubeJS 2101 writes them under the instance's `logs/`, not `kubejs/logs/`):
  `minecraft/logs/kubejs/startup.log`, `server.log`, `client.log`, and `minecraft/logs/latest.log`.

## Generated data

`tools/gen_finds.py` owns the stage advancements, the "found" advancements and the stage-finds loot modifiers
under `kubejs/data/` (see the list at the top of the script). Don't hand-edit those JSON files: change the
config in the script, then run `python -I tools/gen_finds.py` and `packwiz refresh`.

The quest book in `config/ftbquests/quests/` was generated **once** by `tools/gen_quests.py` (one chapter per
stage). From now on it is edited in game: open the book, toggle edit mode (needs op), and FTB Quests saves straight
into this repo through the dev-instance symlink. Re-running the script needs `--force` and discards those edits.
In v0.1.10 the book was rebuilt by `tools/quest_book/` (see its README) into hub layouts with topic chapters,
keeping every existing quest ID so progress carried over; that rebuild starts from the v0.1.9 book, discards
in-game edits and gives the quests it added new IDs each time (resetting progress on them), so `rebuild.sh` now
refuses to run without `--new-ids`: extend the live book in place instead. Its art (title banners, the Pokédex panel, the wormhole, Paradox tiles,
gold panels) comes from `tools/gen_quest_art.py` into `kubejs/assets/campfiremons/textures/quests/`; chapter
images reference those, and type icons and big ball pictures straight from Mega Showdown's and Cobblemon's jars.
Quest text lives in one table, `lang/en_us.snbt`, keyed by object ID (`quest.<id>.title`, `chapter.<id>.title`): if a
quest gets a new ID, move its text too (a re-ID in 800a3cb left 21 quests untitled until v0.1.10). FTB Quests 2101
only reads `lang/<locale>.snbt` files; a `lang/en_us/` folder of per-chapter files (which the in-game editor wrote
before) loads as an empty table, so every quest and chapter shows untitled. v0.1.10 shipped that way; v0.1.11 merged it.
Object IDs must stay below `8000000000000000` (FTB Quests reads them as signed longs): a higher one gets a new random
ID on every load, losing its text, links and progress. The v0.1.10 builder made half its IDs that way; v0.1.11
cleared their top bit, and `tools/quest_book/validate.py` now flags any.

`tools/gen_shop.py` owns `config/cobbledollars/default_shop.json` (the default shop minus the
Master Ball); re-run it after updating CobbleDollars.

`tools/gen_animation_fixes.py` owns `kubejs/assets/cobblemon/bedrock/pokemon/animations/`. Mods that replace
Cobblemon's Pokémon files (CCC's animations, Mega Showdown's poses) can leave a winning pose asking for an animation
its group doesn't have, which crashes the client when it plays. The tool rebuilds those groups (missing animations
restored from a lower-priority copy, or empty placeholders) and checks none are left. It reads the mods' resource
order from the dev instance's `logs/latest.log` and the resource packs' from `config/defaultoptions/options.txt`,
so sync the dev instance (and launch it once after adding a mod), then re-run it after updating Cobblemon, CCC,
Mega Showdown, CobbleMotion or any other Pokémon model mod or pack. Sources in its `NO_COPY` list (CobbleMotion: All
Rights Reserved) are never copied: a Pokémon whose broken group comes from one goes back to its previous files, and
the tool checks that no written file carries their content.

CobbleMotion is one Modrinth file used twice: `resourcepacks/cobblemotion.pw.toml` (client) and
`datapacks/cobblemotion.pw.toml` (both sides, for its species additions); update both. `packwiz mr add` with
`--meta-folder resourcepacks` also added its Cobblemon dependency as `resourcepacks/cobblemon.pw.toml`: check for and
delete strays like that after adding anything with dependencies.

`tools/gen_drops.py` owns every `species_additions` file under `kubejs/data/` (drop fixes for mods that replace
Pokémon drop tables, plus egg drops). Re-run it after updating Cobblemon or any mod that ships species_additions.

Cobblemon Cities & Structures is pinned (it changes fast). After updating it, check that the 13 leader dialogues in
`kubejs/data/ccs/dialogues/generated/`, the leader advancements in `kubejs/data/ccs/advancement/kanto/`, and the
emptied functions in `kubejs/data/ccs/function/` still match its file names, then re-run
`tools/gen_structure_spacing.py`. `ccs_leaders.js` swaps the CCS gym leaders for RCT trainers by id (`config.js` `ccsLeaders`), and the leader dialogues
summon the same ids as a fallback: if RCT renames a leader, update both.

Data packs: Open Loader loads the game folder's `datapacks/` (packwiz puts Modrinth data packs there with
`datapack-folder = "datapacks"` in `pack.toml`), but those packs rank **above** KubeJS data, so nothing in
`kubejs/data/` can override them. A data pack we need to change is brought into `kubejs/data/` instead, with its
licence notice, and its pristine zip kept in `tools/vendor/` (not shipped) so `tools/gen_structure_spacing.py` still
sees its original structure sets. CobbleTowns: Continued is shipped this way.

`tools/gen_structure_spacing.py` owns the structure placement under `kubejs/data/`: the shared
`campfiremons:surface_structures` set and its empty cell, the `campfiremons:services` set
(`kubejs/data/campfiremons/worldgen/`), and the overrides that empty the old sets, keep looked-up structures on grids
of their own, or spread the rest (`RARER`, `NOT_POOLED` and `OWN_GRID` at the top). It reads the jars and data packs the
pack ships from the dev instance, so sync that first, and re-run it after adding or updating any structure mod; changes only
apply to chunks generated afterwards. A structure that maps or a mod look up must not be on the shared grid (finding
it there generates every candidate cell and can stall the server): the tool finds explorer-map destinations itself,
but add a mod that locates structures in code to `OWN_GRID`.

## Testing stages

A player's stage is their highest `campfiremons:stage/N` advancement. With vanilla `/advancement`:

```
/advancement grant @s until campfiremons:stage/4    # stages 1–4 (the advancement + its parents)
/advancement revoke @s from campfiremons:stage/1    # clears all stages (the advancement + its children)
/advancement grant @s only campfiremons:bypass      # admin bypass for every lock
```

Don't use `through` for this: it also grants all the *children*, i.e. every later stage up to Champion.

Local test fixtures live in `tools/testpacks/` (datapacks, never shipped). Copy them into a dev world with
`sh tools/install-testpack.sh ["<world folder>"]` (default: the newest world), then in game `/reload` and
`/datapack enable "file/<pack>"`; `/datapack disable` turns one off again.

- `campfiremons-test`: the `campfiremons_mega_test` RCT trainer (Radical Red series, optional, never spawns)
  leading with Mega-ready Manectric and a Primal Kyogre. Summon with `/rctmod trainer summon campfiremons_mega_test`.
- `campfiremons-weak-gyms` (generated by `tools/gen_weak_gyms.py`): every stage trainer (Brock … Champion Terry)
  fields one Lv5 Magikarp with Splash, so stage progression can be tested with real wins. Disable it to fight the
  real Radical Red teams.

## Adding or updating mods

```sh
packwiz mr add <modrinth-slug>        # prefer Modrinth
packwiz cf add <curseforge-slug>      # only if the mod isn't on Modrinth
packwiz update <name>                 # bump one mod
```

Then `python3 tools/gen_modlist.py` to refresh the mod list in README.md (CI fails while it's out of date).

Resource packs we turn on by default (our `resourcepacks/` files and mods' built-in packs such as Cobblemon's
Magikarp Jump and regional forms) are listed in `config/defaultoptions/options.txt` (`resourcePacks`, applied on a
player's first launch; easiest to copy from the dev instance's `options.txt` after enabling them in game). After `packwiz update` renames one (e.g. the RCT trainer skins,
`RCT Trainers+ [1.7] v2.2.zip`), update that entry too. CobbleSounds ships several files from one Modrinth project,
so each has its own `.pw.toml` (`packwiz mr add --version-filename <file>`, then rename the `cobblesounds.pw.toml` it
writes before adding the next); `packwiz update` may not keep each one on its own file, so update them the same way and check the filenames.
The Soundtrack is an `[option] optional = true, default = true` file: the installer asks players once. The default shader pack works the same way: `shaderPack` in
`config/defaultoptions/extra/config/iris.properties` (currently `ComplementaryReimagined_r5.9.3.zip`).

Modrinth/CurseForge dependency lists can be incomplete (Chipped needs Resourceful Lib and Athena but doesn't say so).
After adding mods and syncing the dev instance, check what the jars themselves require before launching:

```sh
python -I tools/check_deps.py        # lists required mod ids no installed jar provides
python -I tools/check_versions.py    # flags Modrinth builds that aren't for our Minecraft version/loader
python -I tools/check_biomes.py      # for biome mods: which new biomes get no Cobblemon spawns
```

Re-importing the official pack's files at their exact versions (after an official update):

```sh
python -I tools/import_mrpack.py <official.mrpack>   # existing .pw.toml files are skipped
packwiz refresh
```

Official-pack overrides that are deliberately **not** included: the bundled tutorial world, the
FancyMenu title-screen branding/assets, the CraftPresence (Discord status) config and the official tips pack.
We ship only `config/fancymenu/options.txt`, with `modpack_mode` on and the editing overlay off, so players
get the plain title screen with no FancyMenu setup prompts.

## Releasing

`main` is work in progress; players and the server pull the `release` branch.

1. On `main`: bump `version` in `pack.toml`, add a `## vX.Y.Z` section to `CHANGELOG.md`, run `packwiz refresh`,
   and commit. `python3 tools/release/build.py` builds the zips into `dist/` if you want to check them first.
2. Ship it:
   ```sh
   git switch release && git merge --ff-only main && git tag vX.Y.Z
   git push origin main release vX.Y.Z && git switch main
   ```
3. CI (`.github/workflows/release.yml`) publishes the GitHub Release with the Prism zip and the server starter.
   Players get the update on their next Play, and the server on its next restart. Wait 5 minutes after the push
   before restarting the server: GitHub serves the pack's files from a cache that can be up to 5 minutes old
   (`max-age=300`), so an earlier restart can sync the previous version (v0.1.12's first restart did).
   If no Release run appears under the repo's Actions tab, start it by hand: `gh workflow run release.yml --ref vX.Y.Z`.
   (Pushes didn't start any workflow for this repo's first few hours; they have since.)

Changing the Minecraft or NeoForge version also needs action outside the pack: players change the NeoForge version
in Prism (**Edit → Version**) or re-import. For the server, add the new NeoForge installer's sha256 to
`NEOFORGE_SHA256` in `tools/release/build.py` (it refuses to build without one), then upload the new release's
`campfiremons-server.jar`: it installs the new NeoForge on its next start.

## Running the server

The host needs Java 21, 10–12 GB of RAM, file access (SFTP or a web file manager), and a way to choose the server
jar or the startup command (DESIGN.md §8). The starter's `campfiremons-server.jar` does the work on every start: it
installs NeoForge once (checksum-verified), syncs the pack from the `release` branch, then starts NeoForge in the same
JVM through NeoForged's ServerStarterJar, so the memory the host gives Java goes to the server.

1. Upload `campfiremons-<version>-server.zip` from the latest release and unzip it in the server folder (once).
2. Point the host at the launcher, either way:
   - **Custom jar** (most panels): set the server jar to `campfiremons-server.jar`, Java to 21, and the memory
     1–2 GB below the plan's RAM.
   - **Startup command** (or a VPS): `MEMORY=10G sh start.sh`.
   - **The host starts its own NeoForge** and ignores the jar setting (PebbleHost's NeoForge 1.21.1 preinstall does):
     add `-javaagent:campfiremons-server.jar` to the host's JVM startup flags (PebbleHost: Loader Settings →
     Startup Flags). The launcher then runs as a Java agent: it syncs the pack before the host's NeoForge starts,
     and stops the server if the very first sync fails, so it never starts without the mods. NeoForge is the
     host's own (PebbleHost installs 21.1.266; the pack loads cleanly on it, players stay on 21.1.264).
   After extracting on a host that assigns the port (PebbleHost), set `server-port` in `server.properties` to the
   panel's port (the one after the colon in the address): the zip's `server.properties` leaves it at 25565, and
   players get "Connection refused" (this happened on the live server on 2026-11-15).
3. Start the server. The first start installs NeoForge and downloads the mods (a few minutes), then the server stops
   to ask for the EULA: set `eula=true` in `eula.txt` and start again.
4. In the console: `op <you>`, then `whitelist add <name>` for each player (the whitelist is on by default).
5. Pregenerate the land around spawn once (Chunky, server-only), so the first days of exploring don't make the
   server lag while the pack's heavy worldgen catches up. In the console: `chunky spawn` (centres on the world spawn,
   which is in Pallet Town), `chunky radius 3000`, `chunky start`. It works through it in the background while the
   server runs; `chunky progress` shows how far it is and `chunky pause` stops it. With `continueOnRestart: true` in
   `config/chunky/config.json` (set on the live server) a restart resumes it, paused or not: `chunky cancel` drops it
   for good, and `chunky continue` resumes by hand otherwise. Run it while nobody's playing. A bigger radius takes
   longer and fills more disk, so keep an eye on the plan's storage.
6. Optional: link the chat with Discord (Simple Discord Link, server-only). Its first start writes
   `config/simple-discord-link/simple-discord-link.toml` and logs "Missing bot token. Mod will be disabled" until it
   has one; the server runs normally meanwhile. That file isn't part of the pack, so syncs never overwrite it.
   - Make a bot ([SDLink's guide](https://sdlink.fdd-docs.com/installation/bot-creation/)): in the Discord Developer
     Portal, New Application → Bot → Reset Token and copy the token; on the same page turn on the Server Members and
     Message Content intents.
   - In Discord (with Developer Mode on under Settings → Advanced), right-click the channel for the game chat → Copy
     Channel ID.
   - Stop the server and set, in that file, `botToken` under `[botConfig]` and `chatChannelID` under
     `[channelsAndWebhooks.channels]` (plus `eventsChannelID` to put joins, deaths and advancements in a channel of
     their own). Start the server: SDLink encrypts the token in the file on first load and prints an invite link in
     the console; open it to add the bot to the Discord server, then run `reloadbot` in the console (or restart).
     A bot that logged in before it was in the Discord server never gets ready and drops messages ("Tried to
     relay discord message before bot is ready"); this happened on the live server on 2026-11-15.
   - The token is the bot's password: never commit it or paste it anywhere else. If it leaks, Reset Token in the
     portal and put the new one in the file.

Every restart pulls the latest release; if the sync fails (GitHub down), the server starts with the files it already
has. The jar is a launcher: it runs the NeoForge installer and packwiz-installer as short child processes (1 GB heap
each), then the server. Some hosts want to know that before you use one; ask them if their terms are unclear.
`java -jar campfiremons-server.jar --sync-only` stops after the sync.
